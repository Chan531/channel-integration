## 빌드 및 실행 방법

사전 준비물은 Java 21뿐입니다. Gradle은 wrapper(`./gradlew`)가 포함돼 있어 별도 설치가 필요 없습니다.

이 저장소는 두 개의 Gradle 모듈로 구성됩니다.

- `channel-integration` (루트 모듈) — 실제 채널연동 서버, 기본 포트 `8080`
- `mock-supplier` (하위 모듈) — 공급사 A·B를 흉내 내는 Mock 서버, 포트 `9090`

**반드시 Mock 서버를 먼저 띄운 뒤 메인 애플리케이션을 실행해야 합니다.** 메인 앱은 기동 시점에 숙소 매핑을 1회 동기화하는데, 이때 Mock이 떠 있지 않으면 그 시도가 조용히 실패하고(로그로만 남음) 다음 재동기화는 24시간 뒤에나 일어납니다.

```bash
# 1. Mock Supplier 먼저 기동 (9090)
./gradlew :mock-supplier:bootRun

# 2. 메인 애플리케이션 기동 (8080) — 별도 터미널에서
./gradlew bootRun
```

정상적으로 뜨면 아래로 확인할 수 있습니다.

```bash
curl "http://localhost:8080/api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0"
```

매핑 데이터는 `./data/channel-integration.mv.db`(H2 파일 모드)에 저장되며, 앱을 재기동해도 유지됩니다. 완전히 초기화하고 싶으면 이 파일(과 `.trace.db`)을 지우고 다시 기동하면 됩니다.

### 테스트 실행

```bash
./gradlew test
```

테스트는 `mock-supplier`를 코드로 직접 기동해서 검증하도록 구성돼 있어, 별도로 Mock을 띄워둘 필요 없이 이 명령 하나로 전체 테스트가 완결됩니다.


## 설계 의사결정

### 왜 Spring MVC + WebClient인가 (WebFlux 미도입)

Spring WebFlux는 Spring MVC에 비해 적은 스레드로 동시 요청을 처리할 수 있기 때문에 효율적인 것으로 알고있습니다.

하지만 관계형 DB의 블로킹 호출이라는 특징은 Spring WebFlux의 적은 스레드로 동작하는 이점과 전혀 맞지 않습니다.
이를 해결할 수 있는 R2DBC라는 대안이 존재하지만, 리액티브 스트림 숙련도가 낮고 기간 안에 이를 학습하여 활용하기에는 리스크가 크다고 판단했습니다.

따라서 Spring MVC를 활용하고 WebClient의 병렬 호출 이점만 취하는 것이 안전한 선택이라고 생각했습니다.

MVC 자체는 블로킹 방식이지만, 공급사 호출 구간만큼은 WebClient의 Reactor 기반 처리로 병렬화했습니다. 청크·공급사 조합마다 `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())`로 블로킹 호출을 별도 스레드 풀에서 실행하고, 이를 `Flux.flatMap`으로 묶어 동시에 실행되도록 했습니다. 이렇게 하면 요청을 처리하는 MVC 스레드는 그대로 두고, 외부 공급사 호출 구간만 병렬로 처리할 수 있습니다.


### 왜 H2인가 (실행: 파일 모드 / 테스트: 인메모리 모드)

MySQL, PostgreSQL은 별도 서버 프로세스를 띄우고 계정, 네트워크 설정까지 해야하는 반면, H2는 설정이 몹시 단순하다는 특징이 있습니다.

프로젝트에서 공급사가 쓰는 코드와 자사 내부 식별자의 매핑 이외에 따로 저장해야하는 데이터가 없고 무거운 기능이 필요 없을만큼 저장 범위가 작다고 생각하여 H2를 선택했습니다.

H2에는 두 가지 모드가 있는데 같은 공급사 상품은 항상 같은 내부 식별자를 반환해야 한다는 요구사항이 있기 때문에 매핑 데이터가 소실되지 않도록 실행은 파일 모드를, 테스트에서는 데이터가 중요하지 않기 때문에 인메모리 모드를 채택했습니다.


### 표준 요금 필드를 세금 포함 총액으로 통일한 이유

공급사 A는 날짜별로 요금, 세금을 응답하는 반면, 공급사 B는 총 금액을 응답하고 있습니다.

두 공급사를 통합해서 보여줘야 하는 상황에서 공급사 A는 총 금액이 계산 가능하지만 공급사 B는 날짜별로 다른 요금, 세금을 역산할 수 없다고 판단하여 표준 요금 필드를 세금 포함 총액으로 통일했습니다.


### 예약 가능 객실 수 판정 기준과 예약 불가 상품 노출 정책

공급사 A, B 모두 해당 날짜에 남아있는 방의 수를 응답하고 있습니다. 
해당 날짜에 남아있는 방이 있어야 연박이 가능하므로, 예약 가능 객실 수는 남아있는 방의 수의 최소값으로 설정했습니다.

예약 불가 상품은 예약 가능 객실 수를 0으로 응답하는 것으로 결정했습니다.
예약 불가 상품을 응답에서 제외한다면 고객 입장에서 해당 숙소가 남아있는 방이 없어서 응답에서 제외된건지, 해당 숙소가 플랫폼에서 조회되지 않는 숙소인지 구별할 수 없다고 판단했기 때문입니다.


### 공급사 연동 타임아웃(연결 1초 / 응답 4초)을 이렇게 정한 이유

- 연결 1초
  - TCP 연결은 보통 수십 ~ 수백 ms 안에 이루어지는 작업으로 알고 있습니다.
  - 1초가 넘어가면 더 대기하는 의미가 없다고 생각하여 빠르게 연결 시도를 끊도록 1초로 설정했습니다.
- 응답 4초
  - 공급사 호출 API는 병렬로 호출하기 때문에 응답 시간은 곧 우리 API 응답 시간과 연관됩니다.
  - 고객이 검색 결과를 기다릴 수 있는 현실적인 한도를 4~5초로 생각했기 때문에 4초로 설정했습니다.


### 숙박 상품 통합 모델 — 무엇을 표준으로 삼고 무엇을 버렸는가

요금·재고는 원본이 항상 공급사 쪽에 있으므로 별도로 쌓아두지 않고, 검색 시점마다 공급사 API를 그대로 호출해 가져오기로 했습니다. DB에는 공급사 코드와 자사 내부 식별자의 매핑만 저장합니다.

### 매핑을 언제, 어떻게 동기화할지 정한 이유

매핑은 자주 바뀌지 않는 정보라고 판단해, 하루에 한 번 주기적으로 동기화하도록 했습니다. 다만 그것만으로는 서버를 처음 띄웠을 때 매핑이 비어 있는 상태라 검색이 되지 않으므로, 서버 실행 시점에도 초기 데이터를 채우기 위해 한 번 실행합니다.

### 신규 Supplier 추가 시 무엇을 고쳐야 하는가

`SupplierClient` 인터페이스를 구현하는 구현체 하나만 추가하면 됩니다. 서비스 계층은 `List<SupplierClient>`로 모든 구현체를 자동으로 주입받기 때문에 이 부분은 따로 손댈 필요가 없습니다. 다만 그 구현체가 존재하기 위한 사전 준비로 `SupplierCode`에 새 공급사 코드를 추가하고, `SupplierWebClientConfig`에 그 공급사용 `WebClient` 빈(base-url·타임아웃 설정 포함)을 추가해야 합니다.

### 실패 판정을 하나로 통일한 이유

공급사 A는 HTTP 상태 코드(4xx/5xx)로 실패를 알리고, 공급사 B는 항상 HTTP 200을 주면서 응답 본문의 `resultCode`로만 실패를 알립니다. 이 차이를 그대로 두면 위쪽 계층이 공급사마다 다른 방식으로 실패를 판단해야 하므로, 두 방식 모두 하나의 예외(`SupplierUnavailableException`)로 통일해 던지도록 했습니다.

다만 공급사 A가 반환하는 여러 실패 코드 중 `TOO_MANY_HOTEL_CODES`는 예외로 뒀습니다. 이건 공급사 쪽 장애가 아니라 우리가 청크를 잘못 나눠 50개를 초과해서 보낸, 우리 쪽 버그를 알리는 신호이기 때문에, 나머지 공급사 장애 상황과 구분해서 `SupplierChunkSizeExceededException`이라는 별도 예외로 분리했습니다.


### 재시도 정책 (선택 구현)

공급사 호출이 `SupplierUnavailableException`(공급사 장애·타임아웃)으로 실패하면 지수 백오프로 최대 2회 재시도합니다(총 3회 시도, 200ms부터 시작해 매 시도마다 2배씩 증가). 등차가 아니라 지수로 늘리는 이유는, 공급사 스펙에 `429 RATE_LIMIT_EXCEEDED`가 정의돼 있기 때문입니다 — 이미 과부하 상태인 공급사를 등차 간격(느리게 벌어짐)으로 다시 두드리면 오히려 회복을 방해할 수 있어서, 간격을 빠르게 벌리는 지수 백오프가 더 안전하다고 판단했습니다. `SupplierChunkSizeExceededException`(우리 쪽 청크 분할 버그)은 재시도해도 결과가 달라지지 않으므로 재시도 대상에서 제외했습니다.

재시도 정책은 공급사 어댑터마다 반복 정의하지 않도록 `SupplierRetrySpec` 공용 헬퍼로 분리했습니다. 재시도 횟수·백오프 간격 같은 공통 정책은 이 헬퍼가 갖고, "무엇을 재시도할지" 판단만 각 어댑터가 자신의 예외 타입에 맞게 넘겨줍니다. 신규 Supplier를 추가할 때도 이 헬퍼를 그대로 재사용하면 됩니다.


### 숙소가 수천 개로 늘어난다면 어떻게 처리할지

공급사 재고·요금 조회 API가 한 번에 최대 50개 숙소만 받기 때문에, 숙소가 많아져도 요청 하나의 크기는 항상 50개로 고정됩니다. 늘어나는 건 요청 하나의 크기가 아니라 필요한 요청(청크)의 개수입니다. 예를 들어 숙소가 2,000개면 공급사 1곳당 청크 40개, 두 공급사를 합쳐 검색 한 번에 HTTP 요청 80개가 나갑니다.

이 청크들은 Reactor의 `Flux.flatMap`으로 병렬 실행되는데, `flatMap`은 기본적으로 동시 실행 개수를 256개로 제한하고 그 이상은 자동으로 큐잉합니다. 청크 개수(= 전체 숙소 수 ÷ 50, 두 공급사 합산)가 256을 넘으려면 숙소가 대략 1만 2천 개는 넘어야 하므로, "수천 개" 규모에서는 이 기본값 안에서 이미 안전하게 처리됩니다. 별도로 동시 실행 개수를 제한하는 코드를 추가하지 않은 이유입니다.

클라이언트 응답에 페이지네이션은 적용하지 않았습니다. 최소 계약이 보유 숙소 전체를 하나의 응답으로 반환하도록 요구하고 있어 기본 동작은 그대로 뒀습니다. 다만 숙소가 지금보다 훨씬 많아져서 응답 데이터 자체가 커진다면, 정렬·페이지네이션을 선택적 파라미터로 추가하는 것도 좋아 보입니다.
