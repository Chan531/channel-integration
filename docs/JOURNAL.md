## Day 1 — 요구사항 이해, 기술 스택/DB 결정

### 수행 내용
- 저장소 초기화, 커밋 컨벤션 정리
- 요구사항 파악, 필수/선택 구현 범위 구분
- 기술 스택 결정: Spring MVC + WebClient
- DB 결정: H2 (실행은 파일 모드, 테스트는 인메모리 모드)

### 의사결정
- **Spring MVC + WebClient, WebFlux 미도입**: WebFlux가 적은 스레드로 동시 요청을 처리한다는 점은
  이론적으로 유리하지만, 관계형 DB에 JPA(블로킹)를 쓰기로 한 이상 WebFlux 이벤트 루프에 블로킹
  호출이 섞이는 구조적 리스크가 있다. 이를 피하려면 R2DBC가 필요한데 리액티브 스트림 숙련도가
  낮고 7일 안에 안정적으로 적용하기엔 리스크가 크다고 판단해, MVC 위에서 WebClient의 병렬 호출
  이점만 취하기로 했다.
- **H2 파일 모드(실행)/인메모리 모드(테스트) 분리**: "같은 공급사 상품은 항상 같은 내부 식별자를
  반환해야 한다"는 요구사항 때문에 재기동 시 매핑 데이터가 소실되면 안 된다. 별도 DB 서버 없이도
  이 요구를 만족시키는 절충으로 파일 모드를 선택하고, 테스트는 격리를 위해 인메모리로 분리했다.

### 시행착오
- AI(Claude)가 WebFlux 미도입 근거로 처음 제시한 논리는 "이 프로젝트에서 동시성이 필요한 곳은
  검색 요청뿐이라 WebFlux까진 필요 없다"는 것이었다. 이 논리가 자기모순이라는 걸 내가 짚었다 —
  트래픽이 몰리는 지점이 하나뿐이라는 건 오히려 WebFlux가 유리해지는 조건이지, 불필요해지는
  조건이 아니기 때문이다. 이 지적을 받고서야 트래픽 볼륨과 무관하게 성립하는 구조적 근거(블로킹
  DB + 논블로킹 이벤트 루프의 조합 리스크)로 다시 세워 최종 결정에 반영했다.

## Day 2 — 도메인 모델, 요금 통합 모델, Mock 서버

### 수행 내용
- `SupplierHotel`/`SupplierRoom` 매핑 엔티티 설계
- 요금 통합 모델 확정 (표준 요금 필드, 예약 가능 객실 수 판정, 예약 불가 상품 노출 정책)
- Mock Supplier를 별도 Gradle 모듈로 구성

### 의사결정
- **매핑 테이블은 코드 ↔ 내부 식별자만 최소 저장**: 숙소명·객실명까지 캐싱할지 고민했으나, 재고·
  요금 조회 API 응답에 그 정보가 항상 함께 오기 때문에 검색 시점에 그때그때 가져오면 된다. 매핑
  테이블에 이름/가격을 얹지 않기로 했다.
- **표준 요금 필드 = 세금 포함 총액 하나**: 공급사 A는 날짜별 단가+세금(net)을, B는 세금 포함
  총액(gross)만 준다. 공통분모가 "기간 전체 세금 포함 총액"뿐이라, A는 `Σ(nightlyRate +
  taxAmount)`로 합산하고 B는 `totalPrice`를 그대로 써서 두 값을 같은 기준(gross)으로 맞췄다.
- **예약 가능 객실 수 = 기간 내 날짜별 재고의 최솟값**: 연박 시 가장 재고가 적은 날이 병목이 되기
  때문이다.
- **예약 불가 상품도 응답에 포함하고 0으로 노출**: 응답에서 빼버리면 "애초에 검색 대상이 아님"과
  "대상은 맞는데 재고가 없음"을 고객이 구별할 수 없어서, 재고 0인 상태로 노출하기로 했다.
- **Mock Supplier는 별도 Gradle 모듈**: 같은 모듈 안에 실행 클래스만 추가하는 방법도 가능했지만,
  컴포넌트 스캔 범위가 겹쳐 Mock 컨트롤러가 실제 앱 기동 시 함께 스캔될 위험이 있다. 별도 모듈로
  분리하면 컴파일 경계와 클래스패스 자체가 나뉘어 이 위험이 원천적으로 없어진다.

### 시행착오
- Mock 서버 구조(같은 모듈 내 별도 클래스 vs 별도 Gradle 모듈)를 두고 두 차례 재검토했다. AI가
  처음엔 "별도 모듈은 설정이 무겁다"고 판단해 별도 클래스 방식을 제안했는데, 내가 "정말 그렇게
  무거운가"라고 재질문하자 AI가 다시 따져보고서 늘어나는 설정이 `settings.gradle` 한 줄과 짧은
  `build.gradle` 하나뿐이라는 걸 확인해 스스로 판단을 뒤집었다. 컴포넌트 스캔 충돌을 원천적으로
  없앤다는 이점이 더 크다고 보고 별도 모듈로 최종 결정했다.

## Day 3 — Supplier 어댑터, 실패 판정 통일, 매핑 동기화

### 수행 내용
- `SupplierClient` 인터페이스 + A/B 어댑터 구현
- 실패 판정 통일 (A: HTTP 4xx/5xx, B: HTTP 200 + 본문 `resultCode` → 하나의 예외로)
- 공급사 연동 타임아웃 설정
- 매핑 upsert 로직(`HotelMappingSyncService`) 구현

### 의사결정
- **실패 판정 통일**: A가 반환하는 여러 4xx/5xx 중 `TOO_MANY_HOTEL_CODES`(우리 쪽 청크 분할
  버그를 알리는 신호)만 별도 예외(`SupplierChunkSizeExceededException`)로 분리하고, 나머지는 전부
  `SupplierUnavailableException`으로 통일했다. B는 상태 코드와 무관하게 본문의 `resultCode`가
  성공 코드(`0000`)가 아니면 같은 예외를 던지도록 맞췄다. 타임아웃도 같은 예외로 통일해, 이 예외
  하나만 보면 공급사가 어떤 방식으로 실패를 알렸는지 위쪽 계층이 신경 쓸 필요가 없게 했다.
- **타임아웃(연결 1초 / 응답 4초)**:
  - 연결 1초 — TCP 연결은 보통 수십에서 수백 ms 안에 끝나므로, 1초가 넘어가면 더 기다릴 이유가
    없다고 봤다.
  - 응답 4초 — 병렬 호출 특성상 이 값이 곧 우리 API의 응답 시간과 직결된다. 고객이 검색 결과를
    기다릴 수 있는 현실적인 한도를 4~5초로 보고 4초로 정했다.
- **외부 호출과 DB 쓰기를 별도 클래스로 분리** (`HotelMappingSyncService`/`HotelMappingWriter`):
  아래 시행착오 참고.

### 시행착오
- 내가 "Upsert인데 왜 이렇게 미리 필터링하는 코드가 복잡한지" 묻고 커밋 전 재점검을 요청하자, AI가
  코드를 다시 훑어보던 중 `HotelMappingSyncService`의 `@Transactional` 범위 안에 외부 HTTP 호출
  (`client.getHotels()`)이 그대로 섞여 있는 걸 스스로 찾아냈다. 같은 트랜잭션 안에 외부 호출이
  있으면 (1) 응답이 느릴수록 DB 커넥션을 그만큼 오래 붙잡고, (2) 한 공급사의 실패가 이미 끝난 다른
  공급사의 DB 반영까지 함께 롤백시킬 수 있다는 문제가 있었다. 외부 호출 담당
  (`HotelMappingSyncService`)과 DB 쓰기 담당(`HotelMappingWriter`)을 별도 빈으로 분리해 해결했다.

  다른 통합 테스트들이 이미 컨텍스트 로딩을 충분히 검증하고 있어 중복이었다.
- 최종적으로 9개 클래스 20개 케이스가 `./gradlew clean test` 8~10초 내에 안정적으로 통과한다.
  (리팩토링 단계에서 레이스 컨디션 가능성을 검토하며 연속 6회 이상 재실행해 재확인했다.)

### 시행착오
- 리팩토링 리뷰 중 DB 유니크 제약을 다시 추가하면서, 내가 "그럼 저장 로직에 try-catch도 필요한 거
  아니냐"고 물었다. AI가 확인해보니 실제 운영에서 매핑을 채우는 경로는 스케줄러 하나뿐이고
  (`@Scheduled(fixedDelay=...)`는 자기 자신과 겹칠 수 없다) 동시 저장이 발생할 경로가 없었다.
  반면 테스트에서 관측됐던 중복 저장은, 테스트 코드가 `@BeforeEach`에서 `syncHotels()`를 수동으로
  또 호출해 앱 기동 시 스케줄러의 자동 실행과 우연히 겹친 것(이중 트리거)이 원인이었다.
  production 코드에 방어 로직을 추가하는 대신, 테스트가 스케줄러의 실행을 기다리기만 하도록 바꿔
  레이스 자체가 생기지 않게 했다.
- 문서화 과정에서 AI가 `SupplierRoom.hotelId`를 `@ManyToOne` 대신 순수 FK 컬럼으로 둔 이유를
  "Room을 조회할 때 Hotel을 함께 로딩할 일이 없어서"라고 썼는데, 내가 "우리는 항상 Hotel을 먼저
  조회하고 그 결과로 Room을 조회하지 않냐"고 지적했다. AI가 실제 코드(`HotelMappingWriter`,
  `InternalRoomOfferResolver` 모두 Hotel 조회 → 그 id로 Room 조회 순서)를 다시 확인해 그 서술이
  틀렸다는 걸 인정하고, "Hotel 조회 자체는 항상 일어나지만 필요한 건 id 값 하나뿐이고 Hotel
  엔티티 객체나 즉시 로딩이 필요한 적은 없다"는 방향으로 정정했다. 이어서 내가 "그럼 즉시 로딩
  (fetch join)이 오히려 유리하지 않냐"고 재차 묻자, AI는 Hotel 쪽에서 join으로 새로 얻을 데이터가
  없고(이미 검색 조건으로 갖고 있던 값), Room 조회가 "한 Hotel의 컬렉션"이 아니라 여러 Hotel에
  걸친 (hotelId, roomCode) 쌍 매칭이라 fetch join으로 대체되지 않으며, 쓰기 경로에서는 오히려
  불필요한 엔티티 참조가 필요해진다는 근거로 답했고, 이 설명을 받아들여 결론을 유지했다.
- 재시도 정책을 추가할 때 AI가 처음엔 `SupplierAClient`/`SupplierBClient` 각각에 재시도 스펙
  (`Retry.backoff(...)`)을 따로 정의했다. 공급사가 늘어날 때마다 같은 재시도 로직을 매번
  반복해야 하는 구조라 내가 지적해서, 재시도 횟수·백오프 간격 같은 공통 정책은
  `SupplierRetrySpec` 공용 헬퍼로 분리하고 "무엇을 재시도할지" 판단만 각 어댑터가 넘겨주는
  구조로 다시 요청해 정리했다.

## 검토했다 폐기한 대안

- **Spring WebFlux 전면 도입**: 이론적으로는 적은 스레드로 동시 요청을 처리할 수 있어 유리하지만,
  이 프로젝트는 관계형 DB에 블로킹 JPA를 쓰기로 했다. WebFlux 이벤트 루프에 블로킹 호출이 섞이는
  리스크를 피하려면 R2DBC가 필요한데, 리액티브 스트림 숙련도가 낮은 상태로 7일 안에 안정적으로
  적용하기엔 리스크가 크다고 판단해 채택하지 않았다. 대신 Spring MVC 위에서 WebClient의 병렬 호출
  이점만 취했다.
